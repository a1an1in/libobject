# 嵌入式软件分层架构设计

## 1. 概述

libobject 项目将嵌入式专用代码统一放在 `src/board`（开发板使用的库）下，分为 **HAL 层**（`src/board/hal`）和 **服务层**（`src/board/service`）。`src/board` 之外的目录（`core`、`net`、`media` 等）都是通用的、跨平台的代码。

嵌入式软件除了 HAL 层，还需要 **服务层**（可复用的硬件相关服务）和 **应用层**（具体项目业务逻辑）。

本文档规划完整的分层架构，重点设计 **服务层**（`src/board/service`）。

## 2. 分层架构总览

```
┌─────────────────────────────────────────────────────────────┐
│  应用层 (Application)          src/app                      │
│  - 具体项目业务逻辑、状态机、产品功能                        │
│  - 只调用服务层接口，不关心底层设备                          │
├─────────────────────────────────────────────────────────────┤
│  服务层 (Service)              src/board/service            │
│  - 可复用的硬件相关服务：存储、温度采集、ADC 采集            │
│  - 屏蔽设备细节，用户只调用服务接口                          │
│  - 可跨项目复用                                             │
├─────────────────────────────────────────────────────────────┤
│  HAL 层 (Hardware Abstraction)  src/board/hal               │
│  - I2c、Uio、Fpga、GPIO、ADC、DAC                           │
│  - 封装硬件寄存器协议，向上提供统一接口                      │
├─────────────────────────────────────────────────────────────┤
│  驱动层 (Kernel Driver)                                     │
│  - Linux 内核驱动：/dev/i2c-N、/dev/uio0                    │
│  - 芯片寄存器、中断、DMA                                     │
└─────────────────────────────────────────────────────────────┘
```

### 2.1 各层职责

| 层 | 目录 | 职责 | 可复用性 |
|----|------|------|----------|
| 应用层 | `src/app` | 具体项目业务逻辑、产品功能 | 不复用 |
| 服务层 | `src/board/service` | 可复用的硬件相关服务，屏蔽设备细节 | 跨项目复用 |
| HAL 层 | `src/board/hal` | 硬件抽象、设备驱动 | 跨项目复用 |
| 驱动层 | 内核 | 硬件寄存器操作 | 无 |

### 2.2 依赖规则

- **上层依赖下层**：应用层 → 服务层 → HAL 层 → 驱动层
- **禁止反向依赖**：HAL 层不能依赖服务层，服务层不能依赖应用层
- **HAL 层只依赖 core**：board 只使用 core 的对象系统、数据结构、工具

### 2.3 HAL 层 vs 服务层

| | HAL 层 | 服务层 |
|---|--------|--------|
| **抽象级别** | 设备相关 | 设备无关 |
| **接口** | 反映设备特性（读寄存器、写字节） | 反映业务功能（save、get_temperature） |
| **示例** | `I2c_EEPROM.read()`、`I2c_TempSensor.read()` | `Storage_Service.save()`、`Temperature_Service.get_temperature()` |
| **用户关心** | 具体设备（EEPROM、温度传感器） | 业务功能（存储、采集） |
| **解决的问题** | 怎么访问这个设备 | 这个功能怎么用 |

**HAL 层**（设备相关）：封装具体硬件设备的访问协议，接口反映设备特性。
- `I2c`：封装 I2C 总线操作（open/read/write/transfer）
- `I2c_EEPROM`：封装 EEPROM 芯片的寄存器协议（读/写字节）
- `I2c_TempSensor`：封装温度传感器的寄存器协议（读温度、设阈值）

**服务层**（设备无关）：基于 HAL 层，提供设备无关的业务接口，屏蔽设备差异。
- `Storage_Service`：提供 `save()`/`load()`，用户不关心底层是 EEPROM 还是 Flash
- `Temperature_Service`：提供 `get_temperature()`，用户不关心是 tmp105 还是 emc1413

**协作关系**：

```
服务层（设备无关）: Storage_Service.save()/load()
        │ 内部选择具体设备
        ▼
HAL 层（设备相关）: I2c_EEPROM.read()/write()
        │
        ▼
驱动层: /dev/i2c-N
```

## 3. 服务层设计（src/board/service）

### 3.1 设计动机

服务层存放**可复用的硬件相关服务**。核心设计思想：

> **设备访问都通过服务，用户不用知道更多细节。**
> 例如存储数据，用户只调用 `save()`/`load()`，不用知道底层是 EEPROM、Flash 还是其他设备。

服务层特点：
- **屏蔽设备细节**：用户只调用服务接口，不关心底层设备
- **和硬件相关**：内部依赖 HAL 层设备类（如 `I2c_EEPROM`、`I2c_TempSensor`）
- **可跨项目复用**：如存储服务、温度采集服务，其他项目也能用
- **不是具体项目业务**：不属于某个特定产品的业务逻辑

因此放在 `src/board/service` 下，与 HAL 层驱动放在一起，可复用性好。

### 3.2 目录结构

```
src/board/
├── CMakeLists.txt                    # 单一库 object-board（hal + service 合并编译）
├── hal/                              # HAL 层：总线 + 设备驱动
│   ├── i2c/                          # I2C 驱动
│   │   ├── I2c.c
│   │   ├── I2c_EEPROM.c
│   │   └── I2c_TempSensor.c
│   └── uio/                          # UIO 驱动
│       ├── Uio.c
│       └── Fpga.c
└── service/                          # 服务层：可复用硬件相关服务
    ├── Storage_Service.c             # 存储服务（屏蔽设备细节）
    └── Temperature_Service.c         # 温度采集服务
```

对应头文件：

```
src/include/libobject/board/
├── hal/                              # HAL 层头文件
│   ├── i2c/
│   │   ├── I2c.h
│   │   ├── I2c_EEPROM.h
│   │   └── I2c_TempSensor.h
│   └── uio/
│       ├── Uio.h
│       └── Fpga.h
└── service/                          # 服务层头文件
    ├── Storage_Service.h             # 存储服务（屏蔽设备细节）
    └── Temperature_Service.h         # 温度采集服务
```

### 3.3 服务设计

服务（Service）封装基于 HAL 层设备类的通用功能，提供**设备无关**的业务接口：

```c
/* 存储服务示例：用户只调用 save/load，不关心底层设备 */
typedef struct Storage_Service_s {
    Obj parent;
    I2c_EEPROM *eeprom;               /* 内部依赖 HAL 层设备类 */

    int (*init)(Storage_Service *svc, int bus, int slave_addr, int size);
    int (*save)(Storage_Service *svc, uint16_t addr, void *data, int len);
    int (*load)(Storage_Service *svc, uint16_t addr, void *data, int len);
} Storage_Service;
```

```c
/* 温度采集服务示例 */
typedef struct Temperature_Service_s {
    Obj parent;
    I2c_TempSensor *sensor;           /* 内部依赖 HAL 层设备类 */

    int (*init)(Temperature_Service *svc, int bus, int slave_addr);
    float (*get_temperature)(Temperature_Service *svc);
    int (*set_alarm_limit)(Temperature_Service *svc, float high, float low);
} Temperature_Service;
```

### 3.4 服务层与 HAL 层的关系

```
应用层 (Product_Logic)
   │ 只调用服务接口，不关心底层设备
   ▼
服务层 (Storage_Service)
   │ 内部依赖 HAL 层设备类
   ▼
HAL 层设备类 (I2c_EEPROM)
   │
   ▼
HAL 层基类 (I2c)
   │
   ▼
驱动层 (/dev/i2c-N)
```

## 4. 应用层设计（src/app）

应用层存放**具体项目业务逻辑**，不复用。业务逻辑只调用服务层接口，不关心底层设备。

```
src/app/
├── CMakeLists.txt                    # 独立库 object-app
├── include/libobject/app/
│   └── Product_Logic.h               # 产品业务逻辑
└── Product_Logic.c
```

## 5. 构建集成

### 5.1 单一库 object-board

`src/board` 下所有代码（hal + service）编译成**单一库** `object-board`。`src/board/CMakeLists.txt` 使用 `file(GLOB_RECURSE)` 递归收集 hal 和 service 子目录的所有 `.c`/`.h`：

```cmake
project(object-board)

file(GLOB_RECURSE MOUDLE_HEADERS "*.h")
file(GLOB_RECURSE MOUDLE_SOURCES "*.c")
file(GLOB MOUDLE_SRC ${MOUDLE_HEADERS} ${MOUDLE_SOURCES})

add_library(${PROJECT_NAME} STATIC ${MOUDLE_SRC})
```

### 5.2 加入构建系统

在 `mk/linux.cmake` 的 `module_lists` 中加入 `src/board`，并在 `ExternalLibs` 中加入 `object-board`：

```cmake
SET (module_lists
    ...
    "src/board"
    ...
)

SET (ExternalLibs
    ...
    object-board
    ...
)
```

## 6. 分层示例：温度监控产品

以"温度监控"产品为例，展示各层协作：

```
应用层: Product_Logic          → 产品业务逻辑（报警、上报、显示）
服务层: Temperature_Service    → 温度采集服务（屏蔽设备细节，可复用）
HAL 层: I2c_TempSensor         → 读温度寄存器、转换温度值
驱动层: /dev/i2c-N             → I2C 控制器
```

## 7. 实施建议

1. **先建服务层**：创建 `src/board/service` 目录，实现服务（如 `Storage_Service`）
2. **先实现一个服务**：如 `Storage_Service`，验证服务层可用
3. **再建应用层**：创建 `src/app`，实现具体项目业务逻辑
4. **保持依赖单向**：严格遵守"上层依赖下层"的依赖规则

## 8. 结论

- **HAL 层**：`src/board/hal`（I2c、Uio、Fpga 等设备驱动）
- **服务层**：`src/board/service`（可复用的硬件相关服务，屏蔽设备细节）
- **应用层**：`src/app`（具体项目业务逻辑）
- **单一库**：`src/board` 下所有代码编译成 `object-board`
- 依赖单向：应用层 → 服务层 → HAL 层 → 驱动层
